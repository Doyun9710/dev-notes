# 2.1.3 주소 지정과 바이트 순서

> Addressing and Byte Ordering

## 핵심 개념

* 프로그램은 메모리를 **바이트의 연속된 배열**처럼 사용
* 각 바이트에는 해당 위치를 식별하는 **주소(Address)** 존재
* 하나의 주소는 CS:APP에서 가정하는 바이트 주소 지정 시스템에서 **1바이트의 위치**를 나타냄

```text
Address      Memory

0x100   →   [ Byte ]
0x101   →   [ Byte ]
0x102   →   [ Byte ]
0x103   →   [ Byte ]
...
```

* `int`, `long`, `double`처럼 하나의 객체가 여러 바이트로 구성될 수도 있음
* 이 경우 객체를 구성하는 바이트들은 연속된 메모리 공간에 저장
* 객체의 주소는 **객체가 차지하는 바이트 중 가장 낮은 주소**

예:

```c
int x;
```

`x`가 4바이트이고 주소가 `0x100`이라면:

```text
x
↓
0x100
0x101
0x102
0x103
```

* 여기서 `&x`가 나타내는 주소는 `0x100`

---

## 멀티바이트 객체의 문제

다음 32비트 값이 있다고 가정.

```text
0x01234567
```

이를 바이트 단위로 나누면:

```text
01 23 45 67
```

각 바이트의 중요도는 다음과 같음.

```text
0x01  → Most Significant Byte
0x23
0x45
0x67  → Least Significant Byte
```

문제는 이 네 개의 바이트를 메모리의 낮은 주소부터 어떤 순서로 저장할 것인가임.

대표적으로 두 가지 방식 존재.

```text
Little Endian
Big Endian
```

---

## 리틀 엔디안 — Little Endian

* **최하위 바이트(Least Significant Byte)** 를 가장 낮은 메모리 주소에 저장하는 방식

값:

```text
0x01234567
```

주소 `0x100`부터 저장한다고 가정하면:

| 주소      | 값    |
| ------- | ---- |
| `0x100` | `67` |
| `0x101` | `45` |
| `0x102` | `23` |
| `0x103` | `01` |

메모리를 낮은 주소부터 보면:

```text
Address       0x100  0x101  0x102  0x103
              ↓      ↓      ↓      ↓

Memory        67     45     23     01
```

원래 숫자는:

```text
0x01234567
```

* 숫자를 사람이 작성하는 순서와 메모리에서 바이트를 읽는 순서가 반대로 보임

### 대표적인 사용 환경

* Intel x86

* x86-64

* AMD64

* 현대의 많은 ARM 기반 시스템

* 특히 CS:APP에서 주요 대상으로 다루는 x86-64 시스템은 little-endian

---

## 빅 엔디안 — Big Endian

* **최상위 바이트(Most Significant Byte)** 를 가장 낮은 메모리 주소에 저장하는 방식

동일한 값을 저장하면:

```text
0x01234567
```

| 주소      | 값    |
| ------- | ---- |
| `0x100` | `01` |
| `0x101` | `23` |
| `0x102` | `45` |
| `0x103` | `67` |

```text
Address       0x100  0x101  0x102  0x103
              ↓      ↓      ↓      ↓

Memory        01     23     45     67
```

* 숫자를 사람이 작성하는 순서와 메모리 바이트 순서가 동일하게 보임

### 사용 사례

* 일부 전통적인 프로세서 및 시스템
* IBM 계열 시스템
* 일부 PowerPC, SPARC 환경
* 인터넷 프로토콜에서 사용하는 **Network Byte Order**

---

## 엔디안이 바꾸는 것은 바이트의 순서

중요한 점은 엔디안이 **비트 자체의 의미를 뒤집는 것이 아니라 멀티바이트 객체를 구성하는 바이트의 배치 순서를 결정한다는 것**

예:

```text
0x01234567
```

각 바이트 자체는 동일.

```text
01
23
45
67
```

달라지는 것은 메모리에서의 배치 순서.

### Little Endian

```text
Low Address
    ↓

67 45 23 01
```

### Big Endian

```text
Low Address
    ↓

01 23 45 67
```

따라서 1바이트짜리 값에는 바이트 순서 문제가 없음.

예:

```c
char ch = 'A';
```

* 객체 자체가 1바이트라면 순서를 결정할 여러 바이트가 존재하지 않음

---

## 엔디안이 평소에는 잘 보이지 않는 이유

일반적인 C 코드에서는 개발자가 직접 바이트 배치를 처리하지 않음.

예:

```c
int x = 0x01234567;

printf("%x\n", x);
```

little-endian 시스템에서도 출력 결과는:

```text
1234567
```

* CPU와 컴파일러가 해당 시스템의 데이터 표현 방식에 맞춰 값을 처리
* 개발자는 일반적으로 논리적인 숫자값만 사용

```text
Program
   ↓
int value
   ↓
Compiler / CPU
   ↓
Memory Representation
```

따라서 대부분의 응용 프로그램에서는 엔디안을 직접 신경 쓸 필요가 없음.

그러나 **메모리의 실제 바이트 표현을 외부에 노출하는 순간** 엔디안이 중요해짐.

---

## 엔디안이 중요해지는 경우 1 — 네트워크 통신

서로 다른 시스템이 멀티바이트 숫자를 그대로 전송한다고 가정.

```text
Machine A
Little Endian

        ↓ Network

Machine B
Big Endian
```

호스트의 메모리 표현을 그대로 전송하고 상대방이 자신의 방식대로 해석하면 동일한 바이트열을 서로 다른 값으로 해석할 가능성 존재.

따라서 통신 프로토콜에서는 **전송되는 바이트 순서를 명확하게 정의해야 함**.

인터넷 프로토콜과 전통적인 소켓 API에서는 **Network Byte Order**, 즉 big-endian 형식 사용.

```text
Host Byte Order
      ↓
Network Byte Order
      ↓
    Network
      ↓
Network Byte Order
      ↓
Host Byte Order
```

대표적인 변환 함수:

```c
htons()
htonl()

ntohs()
ntohl()
```

의미:

```text
h → host
n → network

s → short
l → long
```

예:

```c
uint16_t port = 8080;

uint16_t network_port = htons(port);
```

* 호스트의 바이트 순서와 관계없이 네트워크에서 요구하는 형식으로 변환 가능

> 모든 네트워크 프로토콜이 반드시 big-endian을 사용하는 것은 아님. 프로토콜 명세에서 정의한 바이트 순서를 따르는 것이 핵심.

---

## 엔디안이 중요해지는 경우 2 — 기계어와 디스어셈블리

기계어를 직접 확인할 때 메모리에 저장된 바이트 순서가 노출됨.

CS:APP에서 등장하는 형태의 예:

```text
4004d3: 01 05 43 0b 20 00
```

뒤쪽 네 바이트:

```text
43 0b 20 00
```

little-endian 방식으로 하나의 32비트 값으로 해석하면:

```text
0x00200b43
```

변환 과정:

```text
Memory Byte Order

43 0b 20 00

        ↓ Little Endian interpretation

00 20 0b 43

        ↓

0x00200b43
```

* 여기서 `0x00200b43`은 명령어에 인코딩된 **변위(Displacement)** 값
* 단순한 절대 메모리 주소라고 보는 것은 부정확

따라서 Chapter 3에서 기계어 바이트를 읽을 때 엔디안에 대한 이해 필요.

---

## 엔디안이 중요해지는 경우 3 — 객체의 바이트 표현 확인

C에서는 객체의 주소를 `unsigned char *` 형태로 접근하여 실제 메모리 바이트 확인 가능.

CS:APP에서는 다음과 같은 `show_bytes` 함수 사용.

```c
#include <stdio.h>

typedef unsigned char *byte_pointer;

void show_bytes(byte_pointer start, size_t len) {
    for (size_t i = 0; i < len; i++) {
        printf(" %.2x", start[i]);
    }

    printf("\n");
}
```

정수의 바이트 표현을 확인하는 함수:

```c
void show_int(int x) {
    show_bytes((byte_pointer) &x, sizeof(int));
}
```

핵심 부분:

```c
(byte_pointer) &x
```

원래:

```text
&x
↓
int *
```

캐스팅 후:

```text
unsigned char *
```

* 동일한 메모리 주소를 1바이트씩 접근 가능

```text
int object

┌────┬────┬────┬────┐
│ B0 │ B1 │ B2 │ B3 │
└────┴────┴────┴────┘
  ↑
unsigned char *
```

---

## `unsigned char *`를 사용하는 이유

* C에서는 문자 타입을 통해 객체의 **객체 표현(Object Representation)** 을 바이트 단위로 확인할 수 있음
* 따라서 `show_bytes`는 단순히 숫자의 값을 출력하는 것이 아니라 **메모리에 실제 저장된 바이트 패턴을 관찰하는 코드**

```text
Value
  ↓
Object Representation
  ↓
Individual Bytes
```

이 차이가 중요함.

예:

```c
int x = 12345;
```

논리적인 숫자값:

```text
12345
```

16진수:

```text
0x3039
```

32비트 `int`라고 가정하면:

```text
0x00003039
```

바이트 단위:

```text
00 00 30 39
```

---

## `show_int(12345)`의 결과

### Little Endian

메모리의 낮은 주소부터:

```text
39 30 00 00
```

따라서 `show_int(12345)`의 출력:

```text
39 30 00 00
```

### Big Endian

```text
00 00 30 39
```

동일한 숫자:

```text
12345
```

동일한 32비트 비트 패턴:

```text
00000000 00000000 00110000 00111001
```

하지만 메모리에 배치되는 **바이트 순서만 다름**.

---

## 엔디안과 문자열

문자열은 각 문자가 독립적인 바이트 단위로 저장되는 경우 엔디안의 영향이 일반적인 멀티바이트 정수와 다르게 나타남.

예:

```c
char *s = "12345";
```

ASCII 기준:

```text
'1' → 31
'2' → 32
'3' → 33
'4' → 34
'5' → 35
```

메모리:

```text
31 32 33 34 35 00
```

* 각 문자는 독립적인 1바이트 값
* 따라서 일반적인 ASCII 문자열의 문자 순서가 CPU 엔디안에 따라 뒤집히는 것은 아님

```text
"12345"

Little Endian → "12345"
Big Endian    → "12345"
```

* 엔디안은 **하나의 멀티바이트 값을 구성하는 바이트들 사이의 순서**에서 문제 발생

---

## 개발할 때 왜 중요한가

### 바이너리 파일 파싱

파일 내부에 다음과 같은 32비트 값이 존재한다고 가정.

```text
12 34 56 78
```

이를 어떻게 해석해야 하는지는 파일 포맷의 바이트 순서 규칙에 따라 결정.

Big Endian:

```text
0x12345678
```

Little Endian:

```text
0x78563412
```

* 바이너리 포맷을 분석할 때 엔디안 확인 필수

---

### 네트워크 프로토콜

* 여러 머신 사이에서 동일한 바이트열을 동일한 값으로 해석하기 위해 명시적인 바이트 순서 규칙 필요
* 프로토콜 구현 시 호스트의 엔디안에 의존하지 않는 코드 작성 필요

---

### 디버깅과 메모리 덤프 분석

디버거에서 다음과 같은 메모리를 확인할 수 있음.

```text
67 45 23 01
```

x86-64에서 이를 32비트 정수로 해석한다면:

```text
0x01234567
```

* 메모리 덤프
* Core Dump
* 디버거
* 바이너리 분석
* 리버스 엔지니어링

등에서 필수적인 해석 능력

---

### 직렬화와 역직렬화

메모리의 객체를 그대로 파일이나 네트워크에 기록하면 플랫폼 의존적인 데이터 생성 가능.

```text
Memory Representation
        ↓
   Raw Byte Copy
        ↓
Platform-dependent Format
```

따라서 이식 가능한 데이터 형식에서는 다음 요소를 명시해야 함.

```text
Field Size
+
Byte Ordering
+
Data Representation
```

* 단순히 `sizeof(int) == 4`만 알고 있는 것으로 충분하지 않음
* **그 4바이트가 어떤 순서로 저장되는지까지 고려 필요**

---

## 이후 학습과의 연결

앞 절에서는 객체가 몇 바이트의 공간을 사용하는지 확인.

```text
Data Sizes
    ↓
int = 4 bytes
```

이번 절에서는 그 여러 바이트가 메모리에 어떤 순서로 저장되는지 학습.

```text
Multi-byte Object
       ↓
Byte Ordering
       ↓
Little Endian
Big Endian
```

이는 이후 비트 연산과 정수 표현뿐 아니라 Chapter 3의 기계 수준 프로그램을 이해하는 기반.

```text
Bits
 ↓
Bytes
 ↓
Data Sizes
 ↓
Byte Ordering
 ↓
Integer Representation
 ↓
Machine-Level Representation
```

Chapter 1의 핵심 관점과 연결하면:

```text
Bits + Context
```

동일한 바이트열도 어떤 크기의 객체로 묶고 어떤 바이트 순서로 해석하는지에 따라 의미가 달라질 수 있음.

---

## 정리

* 메모리는 프로그램 관점에서 주소를 가진 바이트들의 배열로 볼 수 있음
* 멀티바이트 객체는 연속된 여러 바이트에 저장됨
* 객체의 주소는 객체가 차지하는 가장 낮은 바이트 주소
* little-endian은 최하위 바이트를 낮은 주소에 저장
* big-endian은 최상위 바이트를 낮은 주소에 저장
* 엔디안은 바이트 자체가 아니라 **멀티바이트 객체를 구성하는 바이트들의 배치 순서**에 관한 규칙
* 일반적인 프로그램에서는 바이트 순서가 추상화되어 잘 드러나지 않음
* 네트워크 통신, 바이너리 파일, 디스어셈블리, 메모리 덤프 등에서는 직접 고려 필요
* C에서는 `unsigned char *`를 이용해 객체의 실제 바이트 표현 확인 가능
* 바이트 순서를 이해하는 것은 이후 정수 표현과 기계 수준 프로그램 분석의 기반

> **엔디안은 값 자체를 바꾸는 규칙이 아니라, 하나의 멀티바이트 값을 구성하는 바이트를 메모리에 어떤 순서로 배치할지 정하는 규칙.**
