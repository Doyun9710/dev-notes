# 2.1.4 문자열은 바이트의 연속으로 표현됨

> Representing Strings

## 핵심 개념

* C 문자열은 메모리에서 **`char` 객체가 연속된 배열** 형태로 표현됨
* 문자열의 끝에는 값이 `0`인 **널 문자(null character) `'\0'`** 저장
* CS:APP의 ASCII 예제에서는 각 문자가 하나의 바이트 값으로 표현됨

예:

```c
char str[] = "hello";
```

메모리의 논리적 구성:

```text
'h'  'e'  'l'  'l'  'o'  '\0'
```

ASCII 값을 16진수로 표현하면:

```text
68 65 6c 6c 6f 00
```

* `"hello"`의 눈에 보이는 문자는 5개
* 실제 배열에는 마지막 `'\0'`까지 포함되어 총 6개의 `char` 객체 존재

```text
"hello"

5 characters
+
1 null character
=
6 char elements
```

---

## C 문자열과 널 문자

C 문자열에서는 별도의 길이 정보가 문자열 자체에 포함되지 않음.

대신:

```text
문자
↓
문자
↓
문자
↓
'\0'
```

형태로 저장하고, `'\0'`을 만나면 문자열의 끝으로 판단.

예:

```c
char str[] = "ABC";
```

메모리:

```text
Address      Value

0x100        'A'
0x101        'B'
0x102        'C'
0x103        '\0'
```

ASCII 기준으로 보면:

```text
41 42 43 00
```

### `'\0'`과 `NULL`의 차이

두 표현은 같은 개념이 아님.

```c
'\0'
```

* 값이 `0`인 문자
* 문자열의 끝을 표시하는 데 사용

반면:

```c
NULL
```

* 널 포인터를 표현하기 위해 사용하는 매크로

따라서 C 문자열에서는 정확히 **null-terminated string**, 즉 널 문자로 끝나는 문자열이라고 표현하는 것이 적절함.

---

## ASCII 문자 표현

CS:APP에서는 문자열 표현을 설명하기 위해 ASCII 사용.

ASCII는 다음 범위의 문자 코드 정의.

```text
0x00 ~ 0x7F
```

즉:

```text
0 ~ 127
```

* 영문 대문자
* 영문 소문자
* 숫자 문자
* 구두점
* 여러 제어 문자

등을 표현.

예:

| 문자     | ASCII 10진수 | ASCII 16진수 |
| ------ | ---------: | ---------: |
| `'0'`  |         48 |     `0x30` |
| `'1'`  |         49 |     `0x31` |
| `'A'`  |         65 |     `0x41` |
| `'a'`  |         97 |     `0x61` |
| `'\0'` |          0 |     `0x00` |

---

## 숫자 문자와 정수 값은 다름

다음 두 값은 서로 다른 의미와 비트 표현을 가짐.

```c
char c = '1';
int x = 1;
```

ASCII 환경에서 문자 `'1'`:

```text
'1'
↓
0x31
↓
49
```

정수 `1`:

```text
1
↓
0x01
```

따라서:

```text
'1' != 1
```

C에서도 실제 비교 결과:

```c
'1' == 49
```

ASCII를 사용하는 환경에서는 참.

이 차이는 Chapter 1에서 다룬 **Bits + Context**와 직접 연결됨.

```text
0x31
```

이라는 바이트를 문자 인코딩 규칙으로 해석하면:

```text
'1'
```

정수로 해석하면:

```text
49
```

* 동일한 비트 패턴이라도 해석하는 컨텍스트에 따라 의미가 달라짐

---

## `"12345"`의 메모리 표현

문자열:

```c
char str[] = "12345";
```

ASCII에서는 각 문자가 다음 값으로 표현됨.

```text
'1' → 0x31
'2' → 0x32
'3' → 0x33
'4' → 0x34
'5' → 0x35
'\0' → 0x00
```

따라서 메모리의 낮은 주소부터 보면:

```text
31 32 33 34 35 00
```

개념적으로:

```text
Low Address
    ↓

31 32 33 34 35 00
 ↑  ↑  ↑  ↑  ↑  ↑
 1  2  3  4  5 \0
```

---

## 문자열과 엔디안

앞 절에서는 멀티바이트 정수의 바이트 순서를 학습.

예:

```text
0x12345678
```

Little Endian:

```text
78 56 34 12
```

Big Endian:

```text
12 34 56 78
```

그러나 ASCII 문자열 `"12345"`는 구조가 다름.

```text
'1' '2' '3' '4' '5' '\0'
```

각 문자가 독립적인 바이트 요소로 배열에 순서대로 저장되므로:

```text
31 32 33 34 35 00
```

* little-endian 시스템에서도 동일
* big-endian 시스템에서도 동일

이유:

```text
Multi-byte Integer

하나의 값
↓
여러 바이트로 분해
↓
바이트 순서 결정 필요
```

반면 ASCII 문자열은:

```text
String

여러 개의 char
↓
각 char가 독립적인 바이트 요소
↓
배열 인덱스 순서대로 저장
```

* 엔디안은 **하나의 멀티바이트 객체 내부의 바이트 배치 순서**에 관한 문제
* 배열 요소 자체의 순서를 뒤집는 규칙이 아님

---

## `show_bytes`로 문자열 확인

앞 절의 `show_bytes`를 문자열에도 사용 가능.

```c
#include <stdio.h>

typedef unsigned char *byte_pointer;

void show_bytes(byte_pointer start, size_t len) {
    for (size_t i = 0; i < len; i++) {
        printf(" %.2x", start[i]);
    }

    printf("\n");
}
```

예:

```c
char str[] = "12345";

show_bytes(
    (byte_pointer) str,
    sizeof(str)
);
```

ASCII 환경에서:

```text
31 32 33 34 35 00
```

* 마지막 `00`까지 확인 가능

참고로:

```c
sizeof(str)
```

은:

```text
6
```

반면:

```c
strlen(str)
```

은:

```text
5
```

### 이유

`sizeof`:

```text
배열 전체 크기
→ '\0' 포함
```

`strlen`:

```text
'\0' 이전까지의 문자 바이트 수
→ '\0' 제외
```

따라서:

```text
"12345"

sizeof(str) → 6
strlen(str) → 5
```

---

## ASCII라는 전제를 구분하기

다음 바이트 표현:

```text
31 32 33 34 35 00
```

은 ASCII 또는 ASCII와 호환되는 문자 인코딩을 전제로 한 결과.

C 언어 자체가 모든 구현에서 반드시 ASCII를 사용하도록 강제하는 것은 아님.

따라서 정확한 표현은:

> ASCII를 사용하는 일반적인 현대 시스템에서 `"12345"`는 `31 32 33 34 35 00`으로 표현됨.

CS:APP이 다루는 일반적인 Linux/x86-64 환경에서는 이러한 가정이 자연스러움.

---

## ASCII를 넘어선 문자 인코딩

ASCII는 128개의 코드만 정의하므로 표현 가능한 문자가 제한적.

예:

```text
English letters
Digits
Basic punctuation
Control characters
```

따라서 다음과 같은 문자 전체를 ASCII만으로 표현할 수 없음.

```text
한글
中文
日本語
é
😀
```

이를 해결하기 위한 대표적인 표준이 **Unicode**.

---

## Unicode와 Code Point

Unicode는 각 문자에 고유한 **코드 포인트(Code Point)** 를 부여.

예:

```text
'A'
→ U+0041
```

```text
'가'
→ U+AC00
```

```text
'😀'
→ U+1F600
```

중요한 점:

> **Unicode 코드 포인트 자체와 그 코드 포인트를 실제 바이트로 저장하는 인코딩 방식은 별개의 개념**

대표적인 Unicode 인코딩:

```text
UTF-8
UTF-16
UTF-32
```

---

## UTF-8

UTF-8은 Unicode 코드 포인트를 **1~4바이트의 가변 길이 바이트열**로 표현.

```text
Unicode Code Point
        ↓
      UTF-8
        ↓
1 ~ 4 bytes
```

### ASCII 호환성

ASCII 영역:

```text
U+0000 ~ U+007F
```

은 UTF-8에서도 동일한 1바이트 값 사용.

예:

```text
'A'

ASCII → 0x41
UTF-8 → 0x41
```

따라서 ASCII 텍스트는 UTF-8에서도 그대로 유효.

---

## UTF-8에서는 문자 하나가 여러 바이트일 수 있음

ASCII에서는:

```text
'A'
↓
1 byte
```

하지만 UTF-8에서는 한글이나 이모지가 여러 바이트 사용 가능.

개념적으로:

```text
'A'
→ 1 byte

'가'
→ multiple bytes

'😀'
→ multiple bytes
```

따라서 일반적으로 다음 두 개념을 동일하게 보면 안 됨.

```text
문자 개수
≠
바이트 개수
```

C 문자열은 기본적으로 `char` 배열이므로 UTF-8 문자열에서도 C가 직접 보는 것은 **문자가 아니라 바이트들의 연속**

```text
UTF-8 text
    ↓
byte sequence
    ↓
char[]
```

---

## UTF-8과 엔디안

UTF-8은 바이트열 자체의 순서가 인코딩 규칙에 정의되어 있으므로 CPU의 little-endian / big-endian에 따라 바이트 순서를 뒤집지 않음.

```text
UTF-8 byte sequence
↓
동일한 순서로 저장
```

이 점에서는 ASCII 문자열과 유사.

반면 UTF-16이나 UTF-32는 하나의 코드 단위가 여러 바이트로 구성될 수 있기 때문에 바이트 순서 문제가 발생할 수 있음.

따라서:

```text
문자열
=
항상 엔디안과 무관
```

으로 일반화하기보다는:

> **ASCII나 UTF-8과 같은 바이트 기반 문자열 표현은 CPU의 엔디안에 의해 문자 순서가 뒤집히지 않음**

으로 이해하는 것이 더 정확함.

---

## C와 UTF-8을 구분해서 이해하기

C 언어 자체가 일반 `char` 문자열의 인코딩을 무조건 UTF-8로 정의하는 것은 아님.

```c
char *s = "hello";
```

이 문자열 리터럴의 실제 실행 문자 인코딩은 구현과 환경의 영향을 받을 수 있음.

현대 Linux 환경에서는 UTF-8 로케일이 매우 일반적이지만:

```text
C language
≠
UTF-8을 항상 강제
```

* 프로그래밍 언어의 문자열 표현
* 문자 집합
* 문자 인코딩
* 운영체제와 locale

을 구분해서 이해할 필요가 있음.

---

## 개발할 때 왜 중요한가

### `strlen()`은 사람에게 보이는 문자 개수를 세지 않음

UTF-8 문자열에서:

```c
strlen(str)
```

은 기본적으로 `'\0'` 이전까지 존재하는 **바이트 수**를 계산.

따라서:

```text
UTF-8 문자 개수
≠
strlen() 결과
```

가 될 수 있음.

* 다국어 문자열 처리에서 매우 중요한 차이

---

### 문자열 버퍼 크기 계산

다음처럼 문자 개수만 보고 버퍼 크기를 결정하면 다국어 입력에서 문제 발생 가능.

```text
10 characters
→ 항상 10 bytes
```

라는 가정은 UTF-8에서는 성립하지 않음.

실제로는:

```text
logical characters
↓
encoding
↓
byte sequence
```

의 관계를 고려해야 함.

---

### 네트워크와 파일 데이터

텍스트를 외부 시스템과 교환할 때 엔디안뿐 아니라 **어떤 문자 인코딩을 사용하는지**가 중요.

예:

```text
UTF-8
ASCII
UTF-16
```

송신자와 수신자가 서로 다른 인코딩을 가정하면 동일한 바이트열을 잘못 해석할 수 있음.

Chapter 1에서 다룬 관점 그대로:

```text
Bits
+
Context
```

문자열에서도 바이트 자체만으로는 충분하지 않으며 **어떤 문자 인코딩으로 해석할 것인지**가 필요.

## 이후 학습과의 연결

앞 절:

```text
Multi-byte Objects
        ↓
Byte Ordering
```

이번 절:

```text
Bytes
 ↓
Characters
 ↓
Strings
```

문자열은 여러 바이트가 메모리에서 어떻게 해석되는지 보여주는 또 다른 사례.

```text
Raw Bytes
    ↓
Character Encoding
    ↓
Text
```

이후에는 비트 수준에서 데이터를 직접 조작하는 연산으로 연결.

```text
Data Representation
        ↓
Boolean Algebra
        ↓
Bitwise Operations
        ↓
Integer Representation
```

## 정리

* C 문자열은 `char` 객체의 연속된 배열
* 문자열 끝은 값이 `0`인 널 문자 `'\0'`으로 표시
* `'\0'`과 `NULL`은 서로 다른 개념
* CS:APP의 ASCII 예제에서는 각 문자가 하나의 바이트 값으로 표현됨
* ASCII 숫자 문자 `'1'`은 정수 `1`과 다른 비트 패턴을 가짐
* ASCII 문자열은 각 바이트가 배열 순서대로 저장되므로 CPU 엔디안에 따라 문자 순서가 바뀌지 않음
* C 언어 자체가 모든 시스템에서 ASCII 또는 UTF-8을 강제하는 것은 아님
* UTF-8에서는 하나의 문자 표현에 여러 바이트가 필요할 수 있음
* 따라서 문자열의 문자 개수와 메모리의 바이트 수를 구분해야 함
* 문자 데이터를 이해하려면 비트와 바이트뿐 아니라 **문자 인코딩이라는 컨텍스트**도 필요

> **C 문자열은 본질적으로 바이트들의 연속이며, 그 바이트가 어떤 문자를 의미하는지는 문자 인코딩 규칙이 결정함.**
